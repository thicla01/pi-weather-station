# v3.3 — Priority Views (7" low-resolution kiosk)

**Status:** Design frozen (2026-06-18). Not yet built. Successor to the v3.2
"3 états radar" work (PR #257), which it builds on rather than replaces.

**Audience:** the maintainer + whoever implements v3.3. Captures *what* and
*why*; the build plan at the end captures *how*.

---

## 1. The problem

The v3.2 MID rail is a **fixed vertical stack** (alert · clock · hero ·
nowcast · air · 2×2 metrics · indoor). It was designed and verified at font
size **M** (the default). The kiosk is run at font size **G** (large, 115 %
zoom), which the maintainer actually uses.

Font size is applied as `zoom` on the app root with a compensating
`height: calc(100dvh / zoom)` (`components/App/index.js`), so at G the
**effective CSS viewport drops from 800×480 to ≈ 696×417** *and* every element
is 15 % taller. Measured on the live 7" target at G with an alert present: the
rail content is **475 px for ≈ 341 px of visible height → ≈ 134 px overflow**,
and the 2×2 metrics fall entirely **below the fold** (reachable only by
scrolling — not glanceable).

**Lesson, now a rule:** design for the **tightest budget (G), not the default
(M)**. If it fits at G it fits at S/M.

The fix is not "shrink everything to fit." It is a different model.

## 2. The model — priority views

Instead of cramming every datum into the rail, the rail shows a small set of
**compact entry-point sections** ("le coup d'œil"). Each entry point expands —
on tap — into its own **full-rail priority view** that reuses the existing
v3.2 MAX mechanism (map shrinks to a thumbnail, the rail gets the screen).

This is a generalization of what v3.2 already does: NowcastLine → MAX
(forecast). v3.3 adds two more views and makes the pattern uniform.

The budget problem disappears: the glance only needs to fit a handful of
one/two-line sections (fits any font size); the detail lives in views that
each have the full rail to themselves.

## 3. Scope — **7" 800×480 touchscreen ONLY**

This model applies **only to the short, low-resolution 7" panel** (the
official Raspberry Pi touchscreen). Everything else keeps the v2/v3.2 stacked
rail unchanged:

| Surface | Layout | Why |
|---|---|---|
| 7" 800×480 **touch** | **priority views (this doc)** | height-starved, and touch makes drill-down work |
| 15" non-touch monitor (the "écurie" display) | LayoutDesktop / stacked rail | larger viewport (everything fits) **and no touch** — drill-down would be impossible, so it must show everything at once |
| 10.1" 800×1280 (tall LayoutPi) | stacked rail | plenty of vertical room |
| Desktop ≥ 1280, Mobile < 800 | unchanged | not the 7" |

This scoping resolves the "non-touch can't tap to drill" concern entirely: the
only non-touch displays in the fleet are the 15" monitors, which do **not** use
the priority-view model. **No context auto-promotion is needed for v1.**

### Gating

LayoutPi is selected by **width** (800–1279 px, `AmbientLayers`). The
priority-view variant is gated **within LayoutPi** on a **height-starved CSS
viewport**: `matchMedia("(max-height: 540px)")` in `priorityViewsEnabled()`
(`client/src/ui/piLayout.js`), plus the `localStorage.forcePriorityViews="on"`
dev override.

> **Correction (2026-07-02).** This originally shipped keyed on
> `window.screen.height ≤ 540` (device height), on the belief that the CSS
> viewport height would flip the model between font sizes (G ≈ 417 px vs
> S ≈ 565 px). That belief was wrong for the v3 zoom mechanism: the font-size
> preference is `zoom` scoped to the `.rail` subtree, so it **never changes the
> viewport height** that `matchMedia` reads — a `max-height` gate is just as
> font-size-stable as `screen.height`, and it fixes two defects the device
> signal had: (a) `screen.height` is blind to `DISPLAY_SCALE`, so a scaled
> 1024×600 panel (CSS 480 — as starved as the 7") was left on the overflowing
> v3.2 rail; (b) `screen.height` reports native px on Chromium but CSS px on
> Firefox under a devicePixelRatio pref, so it could classify identical
> hardware differently per browser. The CSS viewport height is correct on both
> counts and still stable per device (a kiosk viewport is fixed; a
> `DISPLAY_SCALE` change relaunches the kiosk).

The threshold (≤ 540 px) still keeps the roomier 1024×640 10.1" panels on the
v3.2 stacked rail — extending the model to those (per their vertical room) is a
separate policy decision on the threshold, not this signal fix.

## 4. The glance ("le coup d'œil")

Five compact sections, top to bottom. Validated to fit at **G** on the real
**38 %-width / 300 px** right rail (the map keeps 59 % / 470 px — the radar is
the primary surface).

| Section | Role | Expands to | Affordance |
|---|---|---|---|
| **Alert card** (conditional) | danger headline — non-negotiable, always first when present | **Vue Alerte** | whole card tappable, ⤢ corner hint |
| **Clock** (slim) | kitchen-clock: time · date · sunset | — (info only) | none |
| **Hero** | place · actual temp · condition (**no feels-like** — moved to Conditions) | **Vue Conditions** | ⤢ corner |
| **NowcastLine** | "Pluie dans ~20 min" / calm sky message (the radar verdict) | **Vue Prévision** | ⤢ trailing square (as v3.2) |
| **Air (IQA)** | one-line reading (`24 IQA · Risque faible`) | — (tap → its station/pollutant `DetailsPopover`) | chevron |

Rules locked during design:

- **The ⤢ affordance must not add card height** — it is a corner element
  (absolute), never a caption row. Cards keep their v3.2 heights.
- **Not every section opens a full view.** Three do (Alert, Hero, Nowcast).
  The clock and air are info (the air keeps its small detail popover). This is
  the pragmatic reading of "chaque élément se déploie" — only the elements that
  earn a view get one.
- **Title truncation is accepted** on the 300 px rail (the alert title
  ellipsizes; the full text is one tap away in Vue Alerte). Same constraint as
  the v3.2 compact gov card.
- The **"restore N hidden alerts" pill** stays on the glance when dismissals
  exist (already shipped in v3.2 `fa49aaa`) — it is the only way to un-hide a
  dismissed alert, and a dismissed alert removes the alert card entirely.

### Worst-case budget check

Both a gov alert **and** an air-quality alert active + G: the air alert
escalates into the **alert stack** (the `AirAlertCard`, v3.2) and
`suppressAqRow` removes the inline IQA card, so the air datum is never shown
twice and the stack does not overflow. When air is normal, the inline IQA card
shows and there is no air alert card. The two are mutually exclusive by
construction.

## 5. The three priority views

Each view = **map thumbnail + full rail**, reusing the v3.2 `slabPiMax`
mechanism. Returned to the glance via the view's ⤢ (now a minimize) or a back
affordance.

### 5.1 Vue Alerte (from the alert card)

The existing `AlertDetailInline` **promoted to a full view**, plus:

- **Fixed header**: severity chip + source badge (ECCC/NWS) + alert title +
  minimize, with the validity window ("jusqu'à 19 h 30 · NWS Mobile AL").
- **"Aussi actives" selector** (fixed): the *other* eligible alerts as
  tappable severity-dotted chips (e.g. `● Flash Flood Warning` red, `● Flood
  Watch` orange). Tap switches which alert the detail shows. The primary
  (default) is the **most severe** (extreme > severe > moderate). With 3+
  alerts the chip row scrolls horizontally. (This replaces the v3.2 cycle
  counter as the multi-alert navigation surface in this view.)
- **Scrollable structured detail**: the parsed sections `AlertDetailInline`
  already produces (Où · Danger · Observation · Source · Impact · Trajectoire…),
  icon + localized FR lead + the NWS/ECCC body text (NWS body stays English —
  existing decision). Header + selector stay pinned; only the body scrolls.
- **QR footer** (existing) — scan for the upstream bulletin. Kiosk QR-only rule
  applies (no `<a>` links).

### 5.2 Vue Conditions (from the Hero ⤢)

The weather-detail view. Now that the clock and the IQA reading live on the
glance, this holds:

- **Feels-like** (relocated off the glance Hero).
- The **expanded metric set** — the v3.2 2×2 (Wind / Gust / UV / Humidity)
  plus the extras there is finally room for (Pressure, Visibility, Dew point…).
- **Pollen** (when available) and the **indoor** block (when configured).
- The air-quality **detail** (station / pollutant / age) — the same content the
  glance IQA card's popover shows, with room to lay it out.

### 5.3 Vue Prévision (from the NowcastLine ⤢)

The **existing v3.2 MAX** — `ChartTabs` (24 h / 5 days) at full rail. Largely
unchanged; only its `piLayoutState` value is renamed (see §7).

## 6. Severity treatment gradation

"When lives are at stake, drop the subtleties." A ladder, loudest first:

| Severity | Treatment |
|---|---|
| **extreme** (Tornado, Hurricane, Extreme Wind…) | **solid red header band**, white text, prominent icon — in Vue Alerte *and* a matching louder glance card |
| **severe** (red tier — Flash Flood Warning, severe thunderstorm) | tinted header + red left strip + tinted `Avert.` chip — strong but not screaming |
| **moderate** (orange tier) | tinted orange |
| **minor** (yellow / advisory) | opt-in only (`showAdvisoryAlerts`), unchanged |

**No invented safety instructions.** An action line ("take cover", "move to
higher ground") is shown **only when the authority's bulletin contains an
explicit action section** (`alertParser` already classifies the NWS
`PRECAUTIONARY/PREPAREDNESS ACTIONS` block as `action`). When the payload has
none, nothing is shown — the kiosk never authors life-safety guidance.

## 7. State model

Extend the v3.2 `piLayoutState` enum:

```
v3.2:  'min' | 'mid' | 'max' | null
v3.3:  'min' | 'mid' | 'alert' | 'conditions' | 'forecast' | null
```

- `'forecast'` replaces `'max'` (same forecast view; NowcastLine now sets
  `'forecast'`).
- `'alert'` / `'conditions'` are new, each a full-rail priority view.
- `'mid'` is the glance; `'min'` is radar-fullscreen (unchanged); `null` =
  LayoutPi not mounted (unchanged).
- Entry points call `setPiLayoutState('alert' | 'conditions' | 'forecast')`;
  the view's minimize calls `setPiLayoutState('mid')`.
- The derived `piRadarMaximized = piLayoutState === 'min'` shim is unaffected.

The stacked-rail (non-7"/tall) LayoutPi path ignores the new states — they are
only produced by the priority-view variant.

## 8. Build plan (no code until approved)

Builds on v3.2; reuses `slabPiMax`, the framed-card layout, the compact alert
card, `AirAlertCard`/`suppressAqRow`, `AlertDetailInline`, `ChartTabs`.

1. **Gating + state** — short-physical-screen detection within LayoutPi;
   extend the `piLayoutState` enum (`'max'`→`'forecast'`, add `'alert'`,
   `'conditions'`).
2. **Glance variant** — the 5 compact sections with ⤢ corner affordances wired
   to `setPiLayoutState`; Hero loses the feels-like line; air card kept as info.
3. **Vue Alerte** — promote `AlertDetailInline` to a full view + header +
   "Aussi actives" selector; wire the severity-gradation header (incl. the
   extreme red band) and the authority-only action line.
4. **Vue Conditions** — assemble feels-like + expanded metrics + pollen +
   indoor + AQ detail in a full-rail view.
5. **Vue Prévision** — rename `'max'`→`'forecast'`; otherwise the existing MAX.
6. **Severity gradation styling** — extreme band, severe tint, etc.; matching
   louder glance alert card for extreme.
7. **i18n (EN/FR/ES), tests, CHANGELOG, ui-layout docs, ROADMAP** — and a
   visual pass at **800×480 / font size G** (the binding budget) before merge.

Its own PR, a clean v3.3. The v3.2 PR (#257) remains mergeable as-is.

## 9. Open micro-decisions (recommendation in the doc; confirm at build time)

- **Extreme glance card** — when the primary alert is extreme, make the glance
  alert card a notch louder (e.g. red-filled) to match the Vue Alerte band.
  *Reco: yes, a subtle escalation.*
- **Conditions vs glance ownership of air** — the glance owns the IQA reading;
  Conditions owns the AQ *detail* (station/pollutant). Confirm no duplication
  feels redundant on the 7".

## 10. What stays unchanged

Desktop, Mobile, the tall 10.1" LayoutPi, the 15" non-touch monitors, and every
non-7" surface keep their current stacked layout. The radar map, alert data
pipeline, AQ pipeline, and all server endpoints are untouched — v3.3 is a 7"
**presentation** change only.
