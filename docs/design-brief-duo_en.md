# Brief — iPhone Duo layout for pi-weather-station

## Context

**pi-weather-station** is an open-source weather station that runs on a Raspberry Pi 7″ touchscreen in kiosk mode, and is also served as a desktop page and a mobile PWA from the same Express server. It shows real-time weather, an animated radar (RainViewer), forecasts, government alerts (ECCC / NWS), air quality and an AI summary generated by Claude.

**Current stack:** React 19 + CSS Modules, Leaflet + Mapbox tiles, i18next (EN / FR / ES), Express backend, deployed on 10 Pis in production. The PWA is used in Safari on iOS; no native app, no separate build.

**Three existing layouts,** selected by viewport width (`AmbientLayers`):

- `LayoutMobile` — `< 800 px`: one scroll column (clock · alert · hero · air · 2×2 · radar card · forecast · AI), portrait dock at the bottom
- `LayoutPi` — `800–1279 px`: the 7″ kiosk. Grid `1fr 300px` (map · rail) + dock, framed 10 px gutters, and **three rail states** — MIN (radar owns the screen), MID (split, default), MAX (forecast-forward, map becomes a 190 px thumbnail)
- `LayoutDesktop` — `≥ 1280 px`: full-bleed map, floating hero band, rail 320, dock

**iPhone Duo = a new target,** not necessarily a new layout from scratch. Apple's guidance is explicit: *one compact layout for the outer display, one regular layout for the inner display, and let the layout expand across poses* — no custom layout per pose, no extreme rearrangement when the device folds.

## The device, as a web page sees it

Apple has not published logical resolutions. The CSS viewports below are the physical resolutions ÷ 3; Safari's own bars make the usable height smaller.

| State | Physical | Estimated CSS viewport | Layout served today |
|---|---|---|---|
| Outer display, closed, portrait | 5.4″ · 1398 × 2034 · 460 ppi | **≈ 466 × 678** | LayoutMobile |
| Outer display, landscape | — | ≈ 678 × 466 | LayoutMobile (landscape rules) |
| Inner display, open, landscape | 7.6″ · 1878 × 2670 · 430 ppi | **≈ 890 × 626** | **LayoutPi** (it is a 7.6″ screen) |
| Inner display, open, portrait | — | ≈ 626 × 890 | LayoutMobile |
| One half in Split View (two apps, or two Safari windows) | — | ≈ 445 × 626 | LayoutMobile |

Both displays share the same aspect ratio (≈ 1 : 1.45): open, the inner display is **two outer-display-sized halves side by side, hinge in the middle** (the "three screens" of the press). The inner display is a single folding panel; a nano-texture finish minimises the crease.

**Poses** (Apple lists six): closed · tent (standing on its edges) · fully open, landscape · book (partially folded, vertical hinge) · fully open, portrait · laptop (set down, partially folded, horizontal hinge — the upper half upright, the lower half flat).

**What Safari does NOT expose.** No CSS Viewport Segments, no Device Posture API (Chromium-only as of 2026), no reserved-region API (native SwiftUI / UIKit only). A web page gets: viewport width / height and their changes when the device opens or closes, orientation, `pointer: coarse` / `hover: none`, `display-mode: standalone`, and `env(safe-area-inset-*)` — whether the side camera region is reported as a safe-area inset in landscape is **to be verified on the device**. The hinge position is therefore either a **viewport heuristic** (≈ 890 × 626, coarse pointer → hinge at x ≈ 445) or a **user setting** ("foldable screen — hinge in the middle"). Design as if the hinge line is known; we will decide how it is obtained.

**Apple's rules that translate directly to a web layout** (Human Interface Guidelines, "Designing for iPhone Duo", 2026-09-09):

1. **Reserved regions** — the outer front camera (top corner, expands into the Dynamic Island), the inner camera (only while active), and the **folding region** (only when partially open: it divides the inner display into two usable regions and excludes the centre). Keep important elements clear of the centre when folded; prefer an even number of columns in grids (our 2×2 already is).
2. **Split rule** — a primary + secondary pair splits **horizontally when the area is wider than tall, vertically when it is taller than wide**; when partially folded, each view takes one side. For us: map = primary, rail = secondary.
3. **Vertical controls** — on the outer display (wider and shorter than an iPhone) and on the inner display in landscape, iOS moves toolbars, tab bars, the status bar and the Dynamic Island to a **vertical strip on the camera side**; only the inner display in portrait keeps horizontal bars. In Split View each app puts its controls on its outer edge. Order: navigation at the top, frequent actions next, overflow from bottom to top. Immersive interfaces without bars may span the full width.
4. **Continuity** — same functionality and state across displays and poses; one extra level of hierarchy on the inner display (Mail: list *or* message closed, both open); small adjustments when folding, never a rearrangement.

## Existing design system to respect

Everything below already lives in the Claude Design project **"Design System"** (pi-weather-station Ambient Layers). Read its `readme.md` first — it carries the two rule-sets (kiosk & touch, alerts & status) and the normative-vs-illustrative boundary — then compose from its tokens and cards. Do not restyle; extend.

- **Four palettes** as `data-theme`: `day` (default, cream `#f4f0e8`, amber accent), `dusk` (the dark palette served today), `night` (defined, not reachable yet), `nightRed` (night-vision, everything red — the word carries the tier, never the colour alone). `data-hybrid="light|full"` escalates every slab during a government alert (surface .85 → .96, stronger hairline, amber or red strip).
- **Type** — Geist 400 / 500 / 700 and Geist Mono 500 only, tabular numerals for live values, uppercase mono eyebrows. Density S / M / L scales the rail, never the map.
- **Surfaces** — the slab recipe (`--c-surface`, 1 px `--c-border`, radius 10, hybrid strip), radii 3 → 14 + pill, glass blur 8 px on the dock and map chrome, hit targets ≥ 44 px, `:active` feedback only — **hover paints nothing**, no infinite animation, external links as QR codes only.
- **Components to reuse as-is** — `SourceBadge`, `SeverityChip`, `ConfidencePill`, `MoonGlyph`, `MetricCell`; and the specimen cards for the clock, hero, NowcastLine, air card, alert surfaces, dock, forecast slab. The screen anatomies `pi-7in-mid / min / max`, `desktop-1280` and `mobile-portrait` are the starting points — the Duo work is a variation of `pi-7in-*` (inner display) and `mobile-portrait` (outer display).
- **Icons** — inline SVG on `currentColor` (the code uses Iconify / IBM Carbon for controls); no emoji.
- **Copy** — trilingual EN / FR (Québec) / ES; plausible real data (Montréal, Québec, Winslow AZ), calm **and** alert states, never lorem ipsum. Units follow the user preference.

## What to design

Two layouts and one transition, in this order.

### 1. Inner display, fully open — landscape 890 × 626 (the main deliverable)

Start from `pi-7in-mid`. Put the split **on the hinge**: map on one half, rail on the other, a hinge gutter between them wide enough to survive the partially-folded (book) pose — propose a value and name it as a token (e.g. `--hinge-gutter`). Then answer the three states:

- **MID** — which side gets the map? (Apple: controls on the camera side; the camera is on the trailing edge of the right half in the HIG figures.) What does the rail hold at ≈ 445 px wide and ≈ 570 px tall once Safari's bars are removed — the MID stack (alert · clock · hero · NowcastLine · air · 2×2 · indoor) is ≈ 520 px on the 7″; does anything change?
- **MIN** — radar owning the screen: the map may cross the crease when fully open (nano-texture, single panel) — or should it stay on one half with the timeline on the other? Argue it.
- **MAX** — forecast-forward on a display that already splits in two: forecast on one half and map thumbnail on the other (the thumbnail grows), or the current 190 px thumbnail?

**The dock.** Our `BottomDock` is a horizontal bar. Apple's convention on this display is a vertical strip on the camera side. Show **both options** side by side — (a) dock at the bottom, spanning both halves; (b) vertical dock on the camera edge, Apple order (Map group at the top, System at the bottom, health chip where?) — and recommend one with the trade-offs (reach, hinge avoidance, consistency with the Pi kiosk and with the outer display).

### 2. Inner display, taller than wide — portrait 626 × 890, and the laptop pose

Apple's split rule says vertical: **map above, rail below**. In the laptop pose the horizontal hinge is where the split lands — the upright half becomes the radar, the flat half the rail and the controls, which is a kiosk-like use we want to encourage. Show the fully-open portrait screen and the laptop-pose screen; they should be the same layout with the gutter aligned to the hinge, not two designs.

### 3. Outer display, closed — 466 × 678, and the transition

`mobile-portrait` already fits. Show one screen to confirm what the wider-and-shorter proportion changes (the 56 px clock, the 220 px radar card, the portrait dock) and whether the dock should go vertical on the camera side here too. Then show the **open → close transition**: which elements keep their place, what collapses (Apple: the secondary pane collapses into a single pane), what must never jump. State the state that survives the fold (selected metric tab, radar time position, open popover).

### 4. Split View half — 445 × 626 (verification only)

One screen: the PWA sharing the inner display with another app, controls on our outer edge. Confirm `mobile-portrait` survives at this width and this height; flag what does not.

## Constraints

- **PWA in Safari on iOS 27.1** — no native APIs; nothing may depend on knowing the pose. Every decision must be reachable from viewport size, orientation, `env(safe-area-inset-*)` and a user setting.
- **Same layout across poses** — a fold moves the gutter; it does not rearrange the interface. Controls keep their relative positions.
- **Hinge gutter** — a named token; nothing tappable in the folding region when partially open.
- **Touch-first** — 44 × 44 px targets; no hover states; the map stays at native resolution.
- **Palettes** — every screen in `day` and `dusk`; the alert-bearing screens also in `nightRed`.
- **Safe areas** — the outer camera corner / Dynamic Island, the side control strip, the home indicator; use `env()`-shaped insets and say which edge each one guards.
- **Performance** — one Leaflet instance; the map must not be re-mounted when the device folds (a resize + `invalidateSize()`, nothing more).
- **No new settings, sources or styles** that the codebase does not have — the codebase wins at port time. If a setting is needed (hinge position), say so explicitly as a request, with its default.

## Expected deliverables

1. **Screens at exact CSS sizes**: 890 × 626 (MID · MIN · MAX, dock option a and b), 626 × 890 + laptop pose, 466 × 678, 445 × 626 — in `day` and `dusk`, alert screens also in `nightRed`, calm and alert scenarios, FR copy.
2. **The transition** open ↔ close as a before / after pair with the surviving state listed.
3. **A README of decisions**: hinge gutter value, dock recommendation with rationale, the three-state mapping, the heuristic vs setting recommendation for the hinge, and every place where the mock departs from the design system (there should be none) or from the Pi 7″ layout (list them).
4. **Answers to the open questions** below, each with a one-line rationale.
5. Handoff as the usual **HTML bundle** (self-contained, opens in a browser), linked to the "Design System" project tokens.

## Open questions

1. Vertical dock on the camera edge, or bottom dock across both halves?
2. In MIN, does the radar cross the crease, or does it take one half with the timeline on the other?
3. In MAX, thumbnail as today (190 px) or a half-width map?
4. Hinge position: viewport heuristic (≈ 890 × 626 + coarse pointer) or an explicit user setting — and what is the default?
5. Should the laptop pose get anything the fully-open portrait does not (e.g. the dock on the flat half only)?
6. What is the minimum rail width below which the MID stack should drop to the outer-display arrangement?
