# Pi Weather Station — What We Improved

Pi Weather Station is a self-hosted weather display app running on a Raspberry Pi with a 7" touchscreen. Over the past few months, we made a series of improvements across thirteen main areas:

---

**1. Security hardening**

The original app already anticipated network use — the option to allow remote access was documented from the start. We built on that vision by adding the security layer it needed: API key proxying, access controls, and a strict localhost-only boundary for any write operation. As the threat landscape continues to evolve, we audited the codebase and applied several hardening measures: CORS was locked down, and all third-party API calls (Mapbox, RainViewer, LocationIQ, Tomorrow.io, Anthropic Claude, and sunrise-sunset.org) are now proxied through the Express server, so API keys never appear in the browser's network requests — this applies unconditionally, regardless of how the server is started. The remote/local boundary was simplified: all write endpoints (`POST`/`PUT`/`PATCH`/`DELETE`) are now unconditionally `localhostOnly`, the `REMOTE_SECURITY` toggle was removed, and `GET /settings` returns masked booleans for API key fields when called from a remote client (real values only return to localhost). The indoor-temperature block (Homebridge host + credentials) is even stripped entirely from remote responses rather than masked. Optional features like remote access (`ALLOW_REMOTE=true`) and the debug panel (`DEBUG=true`) are now configured via systemd drop-in files (`pi-weather-server.service.d/local.conf` and `override.conf`) so the main service file stays a clean mirror of upstream — making the in-app updater's "service file changed" warning a meaningful signal rather than noise.

On the transport side, the server runs over HTTPS using a self-signed certificate generated automatically on first launch. All communication between the browser and the Pi is encrypted, and mixed-content issues — where a browser blocks unencrypted requests from a secure page — are avoided by routing all external API calls through the server. The auto-generated certificate can be replaced with one from a real certificate authority (Let's Encrypt, corporate CA, or `mkcert`) by dropping `cert.pem` and `key.pem` into `server/`; the full procedure, including format conversion from PKCS#12 / DER / encrypted keys and the auto-regeneration caveat, is documented in `docs/ssl-custom-cert_en.md` (and a French companion).

As part of the same effort, outdated dependencies were audited and updated. Key packages — including webpack (v4 → v5), axios, and express — were brought up to date, significantly reducing the number of known vulnerabilities reported by `npm audit`. Notably, the axios update addressed a known SSRF vulnerability. Ongoing vulnerability scanning and automatic security patches are now handled by Dependabot on GitHub: weekly grouped pull requests for both server and client dependencies, reviewed and merged in development where they can be tested, then propagated to every Pi through the in-app updater's `npm ci` install. The previous `npm audit fix` step inside `install.sh` was removed because per-device fix runs produced patches that were untested, inconsistent across Pis, and only triggered at install time anyway — Dependabot replaces it with a single tested baseline shared by all Pis.

---

**2. API key protection and quota management**

Weather data from Tomorrow.io was previously fetched directly by the browser, exposing the API key and consuming one quota slot per connected client per refresh. Calls are now proxied server-side with a shared cache (15 min / 30 min / 6 h depending on the endpoint), so the upstream API is hit only once regardless of how many clients are connected or how often the page reloads — a significant saving given Tomorrow.io's strict quota limits. The same proxy architecture applies to all other external services, where the primary benefit is consistent API key protection rather than quota management.

---

**3. Automated installation and clean uninstall**

The project had grown more complex to install over time — not by design, but because external dependencies evolved: API changes, new Raspberry Pi OS versions, the transition from X11 to Wayland, and variations in the Chromium binary name across releases. We replaced the scattered manual steps with a guided `install.sh` script that handles Node.js version checks, dependency installation, API key configuration, SSL certificate generation, and startup configuration automatically. Beyond convenience, automation reduces the risk of human error that manual multi-step installations inevitably carry. A matching `uninstall.sh` cleanly reverses every change. Both scripts prompt with clear yes/no defaults so nothing happens by surprise.

Before doing anything else, the installer now runs pre-flight checks for `curl` and `git` and offers to install them via `apt-get` or `zypper` if missing — without `curl`, the NodeSource setup script would silently fall back to the distribution's old `nodejs` package without `npm`, a hard-to-diagnose failure mode that bit early adopters. The Homebridge prompt for the indoor-temperature feature was similarly hardened: instead of asking for the exact `serviceName` string up front (which the user typically had to track down via a `curl` + `jq` recipe before re-running install), the script now queries `/api/auth/login` and `/api/accessories` itself, filters services exposing `CurrentTemperature` / `CurrentRelativeHumidity` / `AirQuality`, and presents a numbered list with capability tags so the user picks by number. Falls back gracefully to manual entry on auth failure or empty list.

Node.js 22 is now installed on all supported platforms: via nvm on Bullseye 32-bit (`armv7l`), where NodeSource has no packages for that architecture, and via NodeSource everywhere else (Bullseye 64-bit, Bookworm, Trixie). The installer detects the OS and architecture automatically and picks the right method without user intervention beyond confirming the install. nvm installs to the user account and the systemd service is automatically configured to source it at startup via a drop-in override, working around the fact that systemd does not load the interactive shell profile. The uninstall script handles both cases, including cleaning up stale nvm references in shell profile files even when the nvm directory has already been manually removed. A separate Phase 8 in the uninstall script wipes runtime artefacts (caches, request counters, server log) unconditionally, so a "keep project directory" exit lands the working copy as clean as a fresh `git clone`.

A separate bug was also fixed: on Bullseye with X11/LXDE, the installer was creating the autostart file with only `@start-server`, discarding the system default entries for `lxpanel`, `pcmanfm`, and `xscreensaver`. Exiting kiosk mode left a black screen with no taskbar or desktop. The installer now copies the system default first before appending `@start-server`.

---

**4. Flexible kiosk autostart and debug panel**

The kiosk startup logic (launching Chromium in fullscreen once the server is ready) is now unified in a single `start-server` script installed to `~/.local/bin`. It auto-detects the display server (labwc, wayfire, or X11) and the correct Chromium binary name, so the same script works across Raspberry Pi OS versions without modification. Kiosk mode is optional — users who have enabled remote access (`ALLOW_REMOTE=true`) and prefer to access the app from another device on the network can skip it during installation. The server still starts automatically via systemd either way, and `start-server` remains available for manual use. A defensive cleanup was added to handle hostname changes: Chromium's `SingletonLock` symlink encodes the holding process's hostname (a legacy NFS safeguard), which causes the kiosk to silently refuse to launch after a `sudo raspi-config` rename until someone manually clears the lock; `start-server` now reads the lock target before launching and clears the stale lock + companion `SingletonCookie` / `SingletonSocket` files when (and only when) the embedded hostname differs from the current one.

A debug panel (enabled via `DEBUG=true`) provides live visibility into provider operational status (Tomorrow.io, Mapbox, ipapi.co, LocationIQ, EPA AirNow, OpenAQ, MELCC × 2, Environment Canada AQHI, Environment Canada severe-weather alerts, NWS, Anthropic Claude, Homebridge), internet connectivity with latency, network access URLs, cache state, API quota counters, service call history, security events, and server logs. The Services list pre-registers every known external provider at server startup with a neutral "Not yet called" status, so an unused service is no longer ambiguously absent from the table. Diagnostic rows on the hardware side show CPU temperature (`/sys/class/thermal/thermal_zone0/temp`, colour-coded at 60 °C and 75 °C), fan speed in RPM (`/sys/class/hwmon/*/fan*_input`, supports the Pi 5 Active Cooler and Linux laptop fans), the current Leaflet map zoom level, and the AQHI/IQA station name and distance behind the AQI badge — rows for hardware that isn't exposed (fan speed on macOS, brightness on x86) hide entirely rather than showing a perpetual `—`. The same `Font Size` setting that scales the InfoPanel also drives the debug overlay (with its own scale, 1.0× / 1.15× / 1.30×, tuned for a panel that already runs tighter than the main UI), and on small screens the debug overlay extends across the full viewport width instead of leaving a 320 px gutter for the InfoPanel.

---

**5. Internationalization and UI refinements**

The interface is now fully localized in English, French, and Spanish using i18next. A language selector is available in the Settings panel, and the browser's language is detected automatically on first load. All UI strings are covered — weather labels, error messages, settings fields, and the entire debug panel.

As part of the same phase, the debug panel header was reorganized into a two-column layout to reduce its vertical footprint: system information (hardware model, OS, version) on the left, network information (URLs, internet connectivity) on the right. The header now also displays the application name, version number, current Git commit hash, and active branch name when not on `master` — making it easy to confirm which build and branch is running directly from the Pi's screen.

**6. AI weather summary**

An optional AI-generated weather summary was added to the main screen, powered by the Anthropic Claude Haiku model. When an Anthropic API key is configured in the settings, a short natural-language paragraph appears below the forecast charts describing current conditions. A second paragraph adapts to the time of day: during the morning or afternoon it previews the evening (18h–21h), during the evening it previews the overnight period (21h–5h), and at night it previews the next day's forecast. Summaries are generated in the interface language (English, French, or Spanish), cached 15 minutes server-side, and silently hidden when no API key is configured — the feature is entirely optional and the app functions fully without it.

Weather data used to build the prompt is reused from the shared server-side cache, so enabling AI summaries does not trigger additional Tomorrow.io API calls beyond what the app already makes. The summary section is visually distinguished with a blue left border, a centered "AI SUMMARY / RÉSUMÉ IA / RESUMEN IA" header, and italic text styled differently in dark and light modes. The AI summary also degrades gracefully when Tomorrow.io throttles: a 429 used to make the entire `/api/weather-summary` endpoint return 500 and the section to disappear; now Tomorrow.io failures drop only the affected paragraph from the prompt while the radar analysis (independent of Tomorrow.io) continues to power the rest of the summary.

A shared chart legend was also added above the forecast charts to label the temperature/wind and precipitation curves — replacing the per-chart legends that had been disabled because they compressed the chart area.

**7. Observability KPIs, license cleanup, and UX polish**

The debug panel gained two new sections giving real-time visibility into both the server and the browser:

- **Server KPIs** track Node.js process uptime, heap memory (used and total) and RSS, the weather cache hit rate with raw hit/miss counts, and a per-endpoint response time table (count, average, min, max) collected by a new Express middleware added to every route.
- **Client KPIs** are collected live in the browser each time the panel opens: page load time from the Navigation Timing API, a live FPS reading measured over one second via `requestAnimationFrame`, JS heap size (available on Chromium-based browsers), and a grouped summary of every `/api/*` call recorded by the browser's Resource Timing API since the page was loaded.

On the license front, a dependency audit revealed two GPL-licensed icon packages (`@iconify/icons-gridicons` and `@iconify/icons-dashicons`) had been included since the project's early versions. Both were replaced with visually equivalent icons from MIT-licensed sets already present in the project (`ion/location-sharp` and `carbon/undo`). The packages were removed from `package.json`. All dependencies are now MIT, ISC, BSD, Apache-2.0, or Creative Commons — no copyleft obligations.

Finally, a small UX fix ensures that opening the Settings panel automatically closes the Debug panel, and vice versa, so both panels can never be visible simultaneously.

**8. Small screen UX and display polish**

The 7" official Raspberry Pi touchscreen (800×480) leaves limited vertical room once the info panel, current weather, and two stacked forecast charts are all visible. Three complementary improvements address this:

First, on screens ≤ 520 px tall, the hourly and daily charts are now shown as tabs ("24 hours" / "5 days") rather than stacked. Only one chart is visible at a time, and switching is instant — each tab keeps its own chart instance without re-fetching data.

Second, a floating toggle button appears on the right edge of the radar map (small screens only) and collapses the info panel entirely, expanding the map to full width. This is particularly useful when monitoring approaching rain. Because Leaflet does not automatically adapt to container size changes, a `MapResizer` component calls `map.invalidateSize()` after a short delay whenever the panel is toggled — without this, the right portion of the map stays white until the user pans or zooms.

Third, a Font Size setting (S / M / L — 85%, 100%, 115% zoom) lets users adapt the info panel to their preference and viewing distance. Applying `zoom` to a container also scales its visual height, which would otherwise push controls off screen or leave a blank area. This is corrected by setting `height: calc(100dvh / zoom)` — restoring the logical height without affecting other layout elements. The forecast charts use a counter-zoom (`zoom: 1 / parentZoom`) so that chart.js measures the container in its natural coordinate space and draws at the right size regardless of the selected font size. Because the InfoPanel's CSS-zoomed contents need a wider column at size L, the panel width now scales in lockstep (255 / 300 / 345 px for S / M / L) so the right column of stats no longer clips the trailing `%` on every value.

On the visual side, the radar legend overlay was restyled to match the app's panel palette: a frosted-glass background (backdrop blur + semi-transparent fill) with a subtle border that switches between dark and light variants, consistent with every other overlay in the UI. The color swatches were also slightly enlarged for better readability at arm's length. The km/h speed unit label was shortened to "kph" to fit more cleanly in the narrow chart axis area.

An "Advanced settings" section at the bottom of the Settings overlay (collapsed by default) hosts a series of display controls that are useful but not part of every user's daily flow:

- **Radar opacity sliders** — separate sliders for light and dark modes (defaults 70 % / 30 %, picked so the radar reads cleanly against each basemap, with a 5 % floor to prevent it from disappearing). The map updates instantly while the slider is dragged; persistence happens via a 500 ms debounce after the user stops moving.
- **Light-mode and dark-mode style selectors** — three light options (`light-v10` / `light-v11` / `streets-v12`) and two dark options (`dark-v10` / `dark-v11`). Light mode defaults to `streets-v12` because its higher contrast keeps city names and the radar's lighter precipitation cells legible where the older `light-v10` faded into the background. The InfoPanel and overlay tints follow the basemap automatically via a single CSS custom property (`--light-panel-bg-rgb`).
- **Default map zoom slider** — range 4–12, persisted in `localStorage`. Slides give an instant live preview via a dedicated `ZoomLevelHandler` so the change is visible without reloading.
- **Distance unit toggle (mi / km)** — explicit choice that drives the radar circles, the sampling-point overlay, and the AI summary's distance vocabulary in lockstep, including rounding the inner / outer rings to clean values per unit (30 / 60 mi vs 50 / 100 km) instead of carrying the same kilometric numbers across both modes.
- **Screen-brightness slider** — range 10–100 %, hidden entirely on hosts without `dtoverlay=rpi-backlight` exposed (HDMI monitors, x86, macOS dev). The slider previews live as the user drags; the actual sysfs write is debounced 250 ms after release. `install.sh` configures the `video`-group udev rule and the `rpi-backlight` overlay end-to-end during the kiosk-mode prompt.

Map tiles were also fixed to render at native 512 px resolution (with the matching `tileSize={512}` and `zoomOffset={-1}` props on the `<TileLayer>`), recovering the resolution that had been silently downscaled to 256 px and produced blurry labels on the kiosk; `maxZoom` was raised from 18 to 20 to make use of `streets-v12`'s headroom.

**9. Multi-distro installability and cold-boot robustness**

The app now installs end-to-end on Raspberry Pi OS (Bullseye / Bookworm / Trixie), Debian / Ubuntu (including Ubuntu 26.04 with GNOME and snap-confined Firefox), and openSUSE Leap 16 (KDE Plasma + native Firefox). The single `install.sh` script detects the distribution, the desktop environment, and the available browsers, then prompts the user to choose between Chromium-family kiosk mode (Chromium, Chrome, Brave, Edge) and Firefox kiosk mode. The choice is persisted in `~/.config/pi-weather-station/browser.conf` so subsequent runs of `start-server` use the right launcher and the right kiosk flags. Snap-Firefox quirks (no `--profile <path>` support) are handled by using a named profile (`-P pi-weather-station`) that Firefox manages itself. On GNOME and KDE the installer also drops an XDG autostart entry so the kiosk launches automatically on user login, on top of the existing Pi OS autostart path.

A second focus was making the server resilient on cold boots. The systemd unit now uses `ExecStartPre` to wait until DNS is reachable before starting Node, the geolocation lookup retries with exponential backoff and caches its result on disk for 30 days, and Node is configured for IPv4-first DNS resolution (`dns.setDefaultResultOrder("ipv4first")`) to avoid IPv6 stalls on networks that advertise it without route. Together these eliminated the silent "blank screen on power-up" failure mode that occurred when the kiosk raced ahead of the network.

**10. Indoor temperature, radar analysis, and the in-app updater**

Three feature additions round out the recent work. First, an **indoor temperature** block was added to the InfoPanel header. When enabled in Settings, the server polls a Homebridge instance (`homebridge-config-ui-x`) on the local network for temperature, humidity, and air-quality readings and renders them next to the clock. The credentials and hostname live under `indoorTemperature.*` in `settings.json` and are stripped entirely from remote `GET /settings` responses for safety.

Second, the radar map draws a 45 km analysis circle (extendable to 90 km / 60 mi via Advanced settings) over the user's location. A server-side `radarAnalyzerCtrl` parses RainViewer tile pixels inside that zone and feeds the result back into the AI summary, which now includes a dedicated radar paragraph describing whether precipitation is currently visible nearby and in which direction it is moving. The radar feature has matured significantly since its initial release — see §13 for the detailed evolution.

Third, an **in-app updater** was added to the Settings overlay. `GET /api/update-check` polls GitHub once an hour for new commits on `master` and returns the list of incoming `feat:` / `fix:` messages. When the user clicks "Update", `POST /api/update` runs three pre-flight checks (rejecting detached HEAD, non-`master` branches, or local uncommitted changes with structured 409 responses), then performs `git pull` + `npm ci` + `systemctl --user restart`. Three other safeguards complete the picture. (1) Installs older than the commit that introduced the `npm install` step are flagged with `needsManualUpgrade` so the modal directs the user to `bash deploy/install.sh` instead — preventing the post-restart crash-loop that would otherwise occur on missing dependencies. (2) If the installed `pi-weather-server.service` differs from the upstream version (because users may have customized it), the modal expands to show the manual `cp` + `daemon-reload` recipe and disables the one-click Update button — the updater can't safely overwrite a file users may have edited. (3) When any pre-flight check or step fails, the server's actual error message is surfaced inside a red bordered box in the modal instead of the button just turning red, so users know exactly what to fix without having to SSH in. Two companion scripts in `deploy/` round out the deployment story: `toggle-remote.sh` flips `ALLOW_REMOTE` on or off without re-running the full install (regenerating the SSL cert with the LAN IP as a Subject Alternative Name when enabling), and `toggle-debug.sh` does the same for the `DEBUG` flag — both edit the systemd drop-in (Linux) or launchd plist (macOS) and reload the service.

**11. Air quality observations from multiple sources, with closest-station selection**

A UV badge and an Air Quality Index badge were added to the InfoPanel header, but the AQI badge initially relied on Tomorrow.io's `epaIndex` field — which requires a paid Air Quality data layer the kiosk owner doesn't have. The badge would silently stay empty for the actual users. Six free, no-cost sources now back the badge in a single orchestrator that runs them in parallel (where possible) and picks the candidate with the smallest station distance:

- **MELCC RSQA Montréal** (Ville de Montréal CSV via `donnees.montreal.ca`) — hourly real-time IQA for the island of Montréal, computed by rolling pollutant readings up to one IQA per station via max-of-pollutants per the official methodology.
- **MELCC RSQAQ provincial** (ArcGIS FeatureServer via `iqa.environnement.gouv.qc.ca`) — hourly real-time IQA for the rest of Quebec (the island of Montréal is excluded by intergovernmental agreement and covered by the Montreal source above).
- **Environment Canada AQHI** (`api.weather.gc.ca`) — Canada-wide, with automatic fallback from `aqhi-observations-realtime` to `aqhi-forecasts-realtime` for stations whose observation pipeline returns zero features (Quebec stations EHTWR and EHHUN at the time of writing). The badge tooltip honestly labels each value as "observed" vs "forecast".
- **EPA AirNow** (per-install API key, free at `docs.airnowapi.org`, rate-limited at 500 calls/h — generous for our 30-min poll) — NowCast 12-hour weighted average for PM2.5 and PM10, 1-hour averages for O3.
- **OpenAQ** (per-install API key, free at `explore.openaq.org/register`) — global fallback covering ~150 countries; the source converts raw concentrations to EPA-canonical AQI using the official breakpoint formula since OpenAQ doesn't pre-compute an index.
- **Tomorrow.io `epaIndex`** — kept as a last-resort fallback for installs that have the paid layer enabled.

The orchestrator at `airQualityCtrl.js` is a thin walker over these sources; each one lives in `server/airQualitySources/` and exposes a normalised `tryAqi(lat, lon)` returning `{value, category, source, scale, kind, stationName, stationDistanceKm}` or `null`. The closest-station picker selects across all hits rather than walking a strict priority chain, so it handles every border zone naturally without hard-coded country gates: a kiosk in Lacolle QC picks MELCC at 5 km over AirNow at 30 km across the border; one in Plattsburgh NY picks AirNow at 5 km over MELCC at 30 km; and a kiosk in Mexico picks OpenAQ at 10 km over AirNow at 80 km. The badge tooltip shows the chosen source plus the station name, distance, and observation/forecast kind so the displayed value is always accountable to its origin. Underlying scales (AQHI 1–10+, EPA 0–500, IQA 0–100) all map to a unified four-tier risk vocabulary (low / moderate / high / very high) so the badge palette and copy stay consistent regardless of which source won.

**12. Government severe-weather alerts in the AlertBanner**

The radar-driven AlertBanner described in §13 covers cells the radar can see, but it stays silent on warnings that aren't really about precipitation: tornado watches, wind advisories, freezing-rain warnings, heat warnings, and so on. A new `GET /api/weather-alerts?lat&lon` endpoint queries two regional sources in parallel and lets a NWS or ECCC alert outrank the radar tier when one is active at orange or red severity:

- **NWS (US)** — free, no API key required (descriptive User-Agent string only). Native `?point=lat,lon` query, server-side filtered by a rough US bounding box so a Quebec kiosk doesn't generate a guaranteed-400 NWS request every poll.
- **Environment Canada** (`api.weather.gc.ca/collections/weather-alerts`) — same pygeoapi instance that already serves AQHI. The collection's `bbox` filter is non-functional on this instance, so the strategy is to fetch all active Canadian alerts once per cycle (≤ 50 features, ~30–100 KB), cache the list server-side for 5 min, and run point-in-polygon locally per request. Bilingual EN/FR is built into every property and preserved through to the client.

When an alert is active, its localised event title (NWS `event` like "Wind Advisory", ECCC `alert_name_en/fr` like "Rainfall warning" / "Avertissement de pluie") plus a `[NWS]` or `[ECCC]` source badge replaces the radar-derived wording. Yellow / minor advisories (small craft, frost watches, etc.) deliberately stay out of the banner — they fire often enough that promoting them to a permanent banner would devalue the louder ones — but they remain in the API payload for future expansion-on-tap UI. Failures are isolated: one source erroring out doesn't blank the other. Outside US/CA, both sources skip the call and the endpoint returns `{ alerts: [] }` (Europe via MeteoAlarm and other regions are a roadmap follow-up).

**13. Radar intelligence — risk tiers, trend awareness, and prompt compression**

The 45 km radar circle introduced in §10 has matured into a tiered analysis pipeline: coloured ring colouring (v1), trend-aware tier bumping for cells heading inward (v2), and hysteresis + per-direction weighting tuned against false-positive screenshots from real kiosk usage (v2.5).

**v1 — Risk-tier ring colouring and the persistent AlertBanner.** The dashed inner / outer circles around the user used to be a constant neutral colour. Now each ring is tinted by the worst-case precipitation intensity sampled on it (calm / yellow / orange / red), aligned with WMO / Météo-France / NWS conventions where intensity drives the colour and worst-case dominates the score. A new `GET /api/radar-risk` endpoint reuses the existing radar analyzer pipeline (5-minute cache, shared tile cache with the AI summary so polling adds zero RainViewer requests on the common path). A persistent `<AlertBanner>` lives between the clock and the scrollable weather section, surfaces a localised one-line message when the ring tier reaches orange or red, and stays out of the way (renders nothing) for calm and yellow — the chromatic shift on the rings is the always-on signal, the banner is the explicit one. Wording differentiates "in your area" (inner ring) from "approaching" (outer ring) so a storm 80 km out reads differently from one already overhead. The sampling-point overlay was upgraded too: each dot now picks its colour from its own intensity instead of being a uniform neutral, so a single glance shows exactly which directions and distances are contributing to the ring score. A centre sample point at `(lat, lon)` itself was added because the inner ring's nearest probes were at 5 km / 3 mi, leaving a hole on the marker — a small cell sitting right on the user (too narrow to extend out 5 km in any direction) would slip through the geometry.

**v2 — Trend-aware bumping for approaching cells.** A "right now" intensity score isn't the whole story; an orange cell heading inward at 60 km/h is more concerning than a stationary orange, and operational meteorology treats imminence as part of the warning. `getRiskLevels` now fetches the same 3-frame sequence (now / -15 min / -45 min) the AI summary already uses, computes a per-direction inward gradient on each ring, and bumps the displayed tier one notch (calm → yellow → orange → red) when a direction shows a precipitation peak that has shifted inward by ≥ 5 km / 3 mi (inner) or ≥ 8 km / 5 mi (outer) over the 45-min window AND its projected arrival at the centre is under 30 min. The bump is gated at `maxIntensity ≥ 2` so light drizzle approaching doesn't escalate the banner. The response carries a `trend` field per ring (`approaching` / `stable` / `leaving`) for diagnostics and future UI use.

**v2.5 — Hysteresis, leaving banner, per-direction weighting.** A series of false-positive screenshots from morning kiosk reads led to three coordinated refinements:

- **Hysteresis on the ring tier.** With 161 inner samples (1 + 16 × 10) and 320 outer samples (32 × 10), letting one rogue pixel decide the tier amplifies sampling noise into full alarm-tier escalations. The tier is now computed from the **2nd-highest** sample on each ring instead of the max — a real precipitation cell large enough to matter typically covers several adjacent samples on the dense grid, so a single hot pixel surrounded by calm neighbours is much more likely sampling noise than a 5 km-wide cell sitting between samples.
- **Leaving banner softening.** When no direction qualifies as "approaching" but at least one shows the symmetric *outward* shift exceeding the per-ring threshold, the ring trend is now `"leaving"` (approaching still wins ties — one band coming in and another going out is still a safety concern). The AlertBanner picks softened copy in that case — *"Précipitations fortes mais s'éloignent" / "Strong precipitation but moving away"* — atones the wording without changing the dashed-circle tier, which still reflects current intensity.
- **Per-direction weighting.** A precipitation band passing the user from approach to recession sits at the same raw intensity throughout; symmetric to the v2 approaching-ring bump, samples whose directions are moving outward by more than the unit-aware shift threshold now contribute their `intensity − 1` to the tier-deciding intensity, while approaching and stable directions keep full weight. Same evidence bar as the existing approaching detection.

The sampling geometry was densified ~10× along the way (57 → 481 points): the inner ring is now 16 directions × 10 distances (every 22.5° × every 5 km / 3 mi from 5–50 km / 3–30 mi); the outer is 32 × 10 (every 11.25° × every 5 km / 3 mi from 55–100 km / 33–60 mi). Each probe also reads a 3×3 pixel neighbourhood instead of a single pixel and returns the worst-case intensity, eliminating the tile-edge anti-aliasing false-clears that single-pixel sampling produced.

The radar block fed to Claude in the AI summary went through a parallel compression pass: directions with no precipitation in the active annulus are omitted entirely, and within an active direction only non-zero samples are listed (the prompt preamble declares the convention so Claude doesn't over-interpret missing entries). On a real Montréal frame, the prompt block went from ~5000 characters to ~2600 (61 % reduction) without any loss of spatial precision in Claude's "Analyse radar" paragraph. A safety net falls back to the legacy uncompressed format whenever the compressed output would actually be longer (rare mid-cluttered geometries). Visually, the radar overlay also benefits from the same Leaflet 512 px tile-rendering fix as the basemap, bringing back native-resolution radar at kiosk zoom levels ≥ 8 where pixels were previously aliased.

Power-user toggles are exposed in Advanced settings: enable / disable the radar analysis entirely (`radarAnalysisEnabled`), extend the sampling radius from 45 km to 90 km / 60 mi (`extendedRadius`), and visualise the analyzer's sample positions on the map (`showSamplingPoints`).
